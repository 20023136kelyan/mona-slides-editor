# Internationalization architecture

Mona uses i18next with react-i18next. English (`en-US`) is the canonical
source locale and runtime fallback. Simplified Chinese (`zh-CN`) is the first
secondary locale. French, Spanish, Italian, German, and Japanese are registered
as planned locales but remain unavailable until their catalogs and layouts are
complete and tested.

## Runtime contract

Locale selection follows this order:

1. the saved choice in `localStorage` under `mona:ui-locale`;
2. the browser's ordered `navigator.languages` preferences;
3. English (`en-US`).

The selected catalog loads before React renders, preventing a wrong-language
flash. English ships in the initial application; secondary catalogs load on
demand. Changing language updates i18next, `<html lang>`, document direction,
and the saved preference without reloading the page.

## Translation boundary

Catalogs own product-interface copy: menus, tooltips, dialogs, validation,
errors, accessibility labels, configuration labels, and product-provided
defaults.

Presentation content is document data. Presentation titles, imported slide
text, user-created text, speaker notes, and template artwork are never
translated automatically. Native font family names remain unchanged so font
matching is not corrupted.

## Files

- `apps/web/src/i18n/index.ts`: initialization, lazy loading, switching,
  persistence, and document metadata.
- `apps/web/src/i18n/locales.ts`: supported/planned locale registry and browser
  detection.
- `apps/web/src/i18n/shared/en-US.json`: canonical shared schema and fallback.
- `apps/web/src/i18n/foundation/en-US.json`: canonical editor/application
  schema.
- Matching `zh-CN.json` files: complete secondary catalogs with identical
  structure.
- `scripts/check-i18n.mjs`: catalog synchronization and untranslated-interface guard.

The language picker currently lives in the settings surface opened from the
avatar menu. Product content such as the presentation title is deliberately
outside that control.

## Adding a language

1. Copy both English catalogs and translate values without changing keys,
   interpolation names, object structure, or array length.
2. Add a lazy loader in `apps/web/src/i18n/index.ts`.
3. Move the locale from `PLANNED_LOCALES` to `LOCALES` in
   `apps/web/src/i18n/locales.ts`.
4. Add its language name to every supported catalog.
5. Run `npm run i18n:check`, `npm run type-check`, `npm run lint`, and
   `npm run build`.
6. Test desktop, dialogs, mobile, slideshow, overflow, keyboard/focus, and font
   behavior in the new locale.

Use semantic feature-scoped keys such as `export.pdf` or
`animationPanel.duration`. Reuse only genuinely identical terms from `common`;
never assemble sentences by concatenating translated fragments. Preserve user
data verbatim and use named interpolation for variable content.

## Enforcement

`npm run i18n:check` verifies identical English/Chinese schemas, rejects Chinese
text in the English catalogs, and scans React/TypeScript source for untranslated
Chinese UI. Native font names are the only allowlisted literals. Every
production build runs this check before compilation.
